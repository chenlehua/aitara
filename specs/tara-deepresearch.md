# **基于ISO/SAE 21434与多模态AI的汽车智能TARA平台架构与实现研究报告**

## **1. 执行摘要**

随着汽车工业向"软件定义汽车"（Software Defined Vehicle,
SDV）的范式加速转型，现代车辆已演变为集成了海量代码、复杂电子电气架构（E/E架构）以及持续云端连接的超级移动终端。这种数字化转型虽然带来了自动驾驶、智能座舱等革命性体验，但也使得汽车网络安全面临前所未有的挑战。车辆攻击面的指数级扩张，使得传统的、基于人工文档的威胁分析与风险评估（Threat
Analysis and Risk Assessment,
TARA）方法已无法满足快速迭代的开发需求及日益严苛的监管要求。

本报告旨在详尽阐述构建一个面向汽车行业的智能TARA平台的架构设计与实现方案。该平台严格遵循
**ISO/SAE 21434** 标准及 **UN R155**
法规要求，利用前沿的人工智能技术与图数据库技术，实现对汽车网络安全风险的自动化、动态化与智能化分析。报告重点针对
**车载信息娱乐系统（IVI）** 和 **远程车载终端（T-BOX）**
这两个核心高风险域进行了深度剖析。

本研究的核心结论是：构建高效的智能TARA平台必须依赖 **图数据库（Graph
Database）**
来构建汽车安全数字孪生，以解决复杂攻击路径的遍历问题；同时，必须引入
**多模态大模型（Multimodal Large Language Model, MLLM）**
来处理工程领域中大量存在的非结构化架构图与技术文档。本方案具体选用
**阿里云百炼平台** 提供的 **Qwen（通义千问）**
系列模型，通过其强大的视觉理解（Qwen-VL）、逻辑推理（Qwen-Max）及语义检索（Qwen-Embedding）能力，打通从"工程图纸"到"风险矩阵"的自动化链路。

报告不仅详细列出了实施TARA所需的输入资料清单，还深入论证了图数据库在资产识别中的不可替代性，以及多模态模型在图纸识别中的必要性，并提供了包含Prompt
Engineering策略、图谱本体设计及API集成流程在内的详细落地指导。

## **2. 行业背景与标准合规性深度解析**

### **2.1 汽车网络安全的严峻形势**

汽车电子电气架构正从分布式的ECU架构向域控制器（Domain
Controller）乃至中央计算（Zonal）架构演进。这种高度集成化不仅意味着算力的集中，也意味着风险的集中。IVI系统作为用户交互的核心，集成了蓝牙、Wi-Fi、5G、USB等多种泛在接口，极易成为黑客的入侵跳板；而T-BOX作为车辆与外界通信的网关，掌握着远程控制（如远程启动、车门解锁）的关键权限，其安全性直接关系到车辆的物理安全。

近年来，针对汽车的攻击手段日益复杂化、工具化。从早期的物理接触式攻击（如通过OBD端口注入CAN报文），发展到如今的远程非接触式攻击（如利用蓝牙协议栈漏洞、伪基站劫持、云端API漏洞）。面对数以亿计的代码行数和复杂的供应链体系，依靠传统的Excel表格进行人工TARA分析，不仅效率低下，且极易因人为疏忽导致关键威胁遗漏，更无法应对车辆全生命周期内的持续风险管理（Continuous
Cybersecurity Management）。

### **2.3 UN R155 与 CSMS 合规要求**

UN R155
法规强制要求OEM必须建立网络安全管理体系（CSMS），并对车辆类型进行网络安全认证。其中核心要求之一是必须证明已对车辆进行了充分的风险评估，并且能够应对已知的网络威胁。智能TARA平台通过内置
**UN R155 Annex 5**
威胁目录，利用RAG（检索增强生成）技术，确保存储库中的每一个威胁场景都在分析过程中被自动检索和校验，从而生成合规性报告，大大降低人工审计成本
。

## **3. 智能TARA平台总体架构设计**

为了实现自动化、智能化的TARA分析，平台采用微服务架构，分为数据层、知识层、推理层和应用层。

### **3.1 架构分层详解**

#### **3.1.1 数据接入层 (Data Ingestion Layer)**

此层负责处理多源异构的工程数据。汽车研发过程中产生的数据格式极其复杂，包括PDF格式的需求规范、Visio/PNG格式的架构图、Excel格式的信号矩阵（DBC）、以及XML格式的ARXML文件。

-   **功能模块**：文件解析器、OCR引擎（Qwen-VL-OCR）、图像预处理器。

-   **关键技术**：利用Qwen-VL的多模态能力，将非结构化的图纸转化为结构化的描述语言。

#### **3.1.2 知识图谱层 (Knowledge Graph Layer)**

这是平台的"大脑"，用于存储车辆的数字孪生模型。

-   **核心组件**：图数据库（Neo4j）。

-   **功能**：存储资产（Asset）、组件（Component）、接口（Interface）、漏洞（Vulnerability）、威胁（Threat）及其之间错综复杂的关系。相比关系型数据库，图数据库在处理多跳关系查询（如"查找从蓝牙接口进入并能影响刹车控制器的所有路径"）时具有天然优势
    > 。

#### **3.1.3 AI推理层 (AI Reasoning Layer)**

基于阿里云百炼平台提供的Qwen系列模型构建。

-   **LLM Core**：使用 **Qwen-Max**
    > 进行复杂的逻辑推理，例如基于组件的功能描述推断其安全属性（CIA）。

-   **RAG Engine**：使用 **Qwen-Embedding**
    > 对历史TARA项目库、CVE漏洞库、Auto-ISAC威胁情报进行向量化存储与检索，辅助LLM进行少样本学习（Few-Shot
    > Learning），减少幻觉，提高分析的专业度 。

-   **Multi-Agent
    > System**：构建多智能体协作系统，模仿安全专家团队（攻击者角色、防御者角色、审计员角色）进行对抗性分析
    > 。

#### **3.1.4 业务应用层 (Application Layer)**

-   **功能**：提供可视化交互界面，展示攻击路径图、风险热力图，并一键生成符合ISO
    > 21434标准的Word/PDF报告。

### **4.2 为什么传统OCR无法满足需求？**

传统的OCR技术只能识别图像中的文字，但无法理解文字与图形之间的空间拓扑关系。例如，在架构图中，识别出"Bluetooth"和"MCU"两个词是不够的，关键在于识别出它们之间有一条连线，且连线上标注了"UART"协议。

-   **空间语义丢失**：传统OCR输出的是文本流，丢失了"左边的框指向右边的框"这种结构信息。

-   **符号识别缺失**：无法识别特定的工程符号（如代表天线的波浪线、代表防火墙的砖墙图标）。

因此，**必须引入多模态大模型（MLLM）**。Qwen-VL不仅能识别文字，还能识别Bounding
Box（边界框），理解组件之间的相对位置和连接关系，从而重构出系统的拓扑结构
。

## **5. 核心技术一：图数据库在资产识别与关联中的应用**

针对用户提问"资产的识别是否需要使用图数据库"，本报告给出明确肯定的回答：**是，图数据库是实现自动化、深层次资产识别与攻击路径分析的必要条件。**

### **5.1 关系型数据库的局限性**

在传统的表格（Excel或SQL）中，资产通常以扁平列表形式存在。然而，汽车网络系统的本质是\*\*图（Graph）\*\*结构------ECU通过总线连接，进程通过IPC通信，功能依赖底层驱动。

-   **关联性丢失**：表格难以表达"数据资产A依赖于组件B，组件B通过接口C连接到外部"这种多级依赖关系。

-   **查询效率低下**：当需要查询"从互联网接口出发，经过任意跳数，最终能影响刹车系统的路径"时，SQL需要进行复杂的递归Join操作，性能极差且难以编写。

### **5.2 基于图数据库的资产建模 (Ontology Design)**

我们采用 **Neo4j** 作为存储引擎，并基于 **UCO (Unified Cybersecurity
Ontology)** 构建汽车安全本体。

#### **5.2.1 节点定义 (Nodes)**

-   :Item (分析对象，如 \"IVI Head Unit\")

-   :Function (功能，如 \"Media Playback\")

-   :Component (组件，分为 Hardware, Software)

-   :Interface (接口，如 \"USB Port\", \"Bluetooth Interface\")

-   :Data (数据资产，如 \"User Contacts\", \"Firmware Image\")

-   :TrustBoundary (信任边界，如 \"Kernel Space\", \"External World\")

#### **5.2.2 关系定义 (Relationships)**

-   (:Component)\--\>(:Interface)

-   (:Interface)\--\>(:Interface)

-   (:Function)\--\>(:Data)

-   (:Data)\--\>(:Component)

-   (:Component)\--\>(:Component) (例如 SoC Host OS)

### **5.3 自动化资产识别流程**

1.  **解析与映射**：利用AI解析BOM和DFD，提取实体。

2.  **图谱构建**：将提取的实体转化为Cypher语句写入Neo4j。

3.  **属性传播**：

    -   **继承逻辑**：如果一个 :Data (用户隐私) 被 \`\` 一个 :Component
        > (Flash
        > Memory)，且该存储器未加密，则图数据库可以通过查询自动推导出该数据资产面临保密性威胁。

    -   **上下文识别**：通过图查询 MATCH (i:Interface
        > {type:\'Internet\'})\--\>(c:Component)，自动将所有与互联网连通的组件标记为"高风险暴露面"，这是单纯看BOM列表无法实现的
        > 。

### **5.4 攻击路径分析的Cypher实现**

图数据库最大的威力在于路径查找算法。以下是一个典型的Cypher查询示例，用于寻找从T-BOX蜂窝接口到车门控制器的攻击路径：

Cypher

// 查找从外部蜂窝接口到车门解锁功能的最短攻击路径

MATCH (source:Interface {access: \'Public_Cellular\'})

MATCH (target:Function {name: \'Door_Unlock\'})

MATCH path = shortestPath((source)\--\>(target))

RETURN path

此查询能瞬间揭示潜在的跨域攻击链（例如：Cellular -\> Modem -\> MCU -\>
Gateway -\> Body Domain -\> Door ECU），这是自动化TARA的核心能力 。

## **6. 核心技术二：多模态大模型在架构图识别中的应用**

针对用户提问"图片的识别是否需要使用多模态大模型"，答案是：**必须使用，且需结合Prompt
Engineering技术。**

### **6.1 架构图处理的挑战**

系统架构图（DFD）包含了极其丰富的语义信息，是TARA分析中识别数据流向和信任边界的黄金标准。但这些信息通常以图片形式存在，非结构化程度极高。

-   **多样性**：不同供应商的图纸风格各异（颜色、形状、线条含义不同）。

-   **复杂性**：线条交叉、文字缩写、图例隐含语义。

### **6.2 阿里云 Qwen-VL 的应用策略**

Qwen-VL（Qwen-Vision-Language）模型具备强大的通用视觉理解能力，能够像人类工程师一样"看懂"图纸。

#### **6.2.1 实现步骤**

1.  **图像预处理**：由于Qwen-VL有分辨率限制（通常支持百万像素级），对于超大幅面的整车E/E架构图，需要进行切片处理（Sliding
    > Window），或者提取关键区域（Region of Interest）。

2.  **提示工程 (Prompt
    > Engineering)**：构建结构化的Prompt，引导模型输出标准格式（如JSON）。

#### **6.2.2 Prompt 示例 (System Prompt)**

角色：你是一位资深的汽车电子系统架构师。

任务：分析上传的系统架构图（System Architecture Diagram）。

要求：

1.  识别图中所有的矩形框，将其定义为"组件（Component）"。

2.  识别图中所有的连线，将其定义为"连接（Connection）"。

3.  提取连线旁边的文字标注，作为"协议（Protocol）"或"数据流（Data
    > Flow）"。

4.  识别任何表示无线连接的图标（如波浪线、天线），标记为"无线接口"。\
    > 输出格式：请严格输出为以下JSON格式，不要包含Markdown标记以外的文本。\
    > {\
    > \"components\":,\
    > \"connections\":\
    > }

#### **6.2.3 图文对齐与纠错**

Qwen-VL输出的JSON可能存在幻觉或坐标偏差。平台需要引入校验机制：

-   **逻辑校验**：例如，模型识别出"CAN总线"连接了"蓝牙天线"，这在工程上是不合理的。利用Qwen-Max（语言模型）对VL模型的输出进行逻辑审查和修正。

-   **人机回环**：在前端界面上，将识别结果（Bounding
    > Box）叠加在原图上，允许工程师手动微调 。

## **7. 核心技术三：基于LLM Agent的自动化分析引擎**

在完成了数据数字化（图数据库构建）后，平台利用 **Qwen-Max**
大语言模型驱动的 Agent 系统执行具体的TARA分析步骤。

### **7.1 Agent 角色设计**

参考 DefenseWeaver 等前沿研究 ，我们设计多智能体协作模式：

1.  **资产解析 Agent**：负责调用Qwen-VL识别图纸，并结合BOM完善资产属性。

2.  **威胁建模 Agent**：基于STRIDE模型，结合资产类型，生成威胁场景。

    -   *输入*：资产=GPS模组，属性=位置数据。

    -   *Prompt*："针对GPS模组的位置数据，基于STRIDE模型中的S（欺骗）和I（信息泄露），生成具体的威胁场景。"

    -   *输出*："威胁1：攻击者使用软件无线电（SDR）发射伪造的GPS信号（欺骗），导致导航系统显示错误位置。威胁2：恶意软件读取GPS缓冲区数据（信息泄露），追踪车辆轨迹。"

3.  **风险评估 Agent**：负责计算攻击可行性和影响。

    -   *知识库调用*：利用RAG技术，从Qwen-Embedding检索CVE数据库，判断类似组件是否有已知漏洞，以此作为"技术复杂度"评分的依据。

### **7.2 自动化 STRIDE 分析逻辑**

平台对每个数据流（Data Flow）自动应用STRIDE规则：

-   **S
    > (Spoofing)**：检查数据源认证机制。如果图中未标注"MAC/Signature"，Agent生成"伪造数据源"威胁。

-   **T
    > (Tampering)**：检查完整性保护。如果协议是明文HTTP或未加密CAN，Agent生成"数据篡改"威胁。

-   **R (Repudiation)**：检查日志审计能力。

-   **I (Information Disclosure)**：检查加密措施。

-   **D (Denial of Service)**：检查资源限流机制。

-   **E (Elevation of
    > Privilege)**：检查访问控制列表（ACL）和调试接口状态。

## **8. 场景深究：车载信息娱乐系统 (IVI) TARA实战**

IVI系统是目前汽车中代码量最大、对外接口最多、最接近消费电子产品的部分，因此也是最高危的攻击面。

### **8.1 IVI 架构与资产盘点**

现代IVI通常基于 **Android Automotive OS (AAOS)** 或 **Linux**
开发，底层运行在高性能SoC（如Qualcomm Snapdragon
8155）上，并通过Hypervisor与仪表盘（Cluster）隔离。

**核心资产 (Graph Nodes)**：

-   **硬件**：Wi-Fi/蓝牙芯片、USB接口、显示屏、音频DSP。

-   **软件**：Android
    > Framework、系统App（导航、电话）、第三方App（Spotify,
    > Zoom）、Web浏览器内核。

-   **数据**：用户通讯录、通话记录、位置历史、OEM证书、数字钥匙。

### **8.2 典型威胁场景与攻击路径**

在智能TARA平台中，针对IVI的分析将重点关注以下路径：

#### **场景 1：恶意App窃取隐私**

-   **威胁**：用户下载了一个伪装的恶意App，该App申请了越权的权限。

-   **攻击路径（图查询结果）**：\
    > App -\> Android Framework -\> Binder IPC -\> Location Service -\>
    > GPS Hardware

-   **AI分析**：Qwen-Max检查App的Manifest文件，发现申请了
    > ACCESS_FINE_LOCATION 权限但应用描述为"计算器"，判定为逻辑异常。

#### **场景 2：蓝牙协议栈远程代码执行 (RCE)**

-   **威胁**：BlueBorne类漏洞，攻击者无需配对即可通过蓝牙控制IVI。

-   **攻击路径**：\
    > External Bluetooth Signal -\> Bluetooth Controller -\>
    > BlueDroid/Fluoride Stack (Vulnerable) -\> Kernel Space -\> Root
    > Shell

-   **AI分析**：通过RAG检索BOM中蓝牙协议栈的版本号，匹配CVE库，发现存在已知漏洞，自动将攻击可行性评级为"高"。

#### **场景 3：通过IVI渗透内网 (Lateral Movement)**

-   **威胁**：攻陷IVI后，向CAN总线发送恶意指令控制车辆。

-   **攻击路径**：\
    > Attacker -\> IVI Shell -\> Gateway Interface (SPI/Ethernet) -\>
    > Vehicle Gateway -\> CAN Bus -\> Body Control Module (BCM) -\>
    > Unlock Door

-   **AI防御建议**：平台检测到IVI与网关之间缺乏严格的防火墙策略，建议增加"网关白名单过滤"机制
    > 。

## **9. 场景深究：远程信息处理器 (T-BOX) TARA实战**

T-BOX是车辆的"调制解调器"，负责所有与云端的通信，是远程控制功能的物理入口。

### **9.1 T-BOX 架构与资产盘点**

T-BOX通常包含一个MCU（处理CAN报文）和一个NAD（Network Access
Device，处理3G/4G/5G通信）。

**核心资产 (Graph Nodes)**：

-   **通信凭证**：APN接入点名称、用户名密码、TSP服务器证书、PKI私钥。

-   **固件**：Bootloader、FOTA更新包。

-   **接口**：LTE天线、eSIM、CAN收发器、调试口（JTAG/UART）。

### **9.2 典型威胁场景与攻击路径**

#### **场景 1：伪基站劫持与降级攻击**

-   **威胁**：攻击者使用IMSI
    > Catcher将信号降级为2G，利用GSM协议弱点拦截短信或注入数据。

-   **AI分析**：TARA平台检查T-BOX配置，如果未强制配置"仅LTE/5G"或未启用双向认证，生成高风险警告
    > 。

#### **场景 2：私有APN网络穿透**

-   **威胁**：许多OEM使用私有APN连接后台，但如果T-BOX内的APN凭证硬编码且泄露，攻击者可直接接入车企内网。

-   **攻击路径**：\
    > Extracted Firmware -\> Hardcoded APN Credentials -\> Connect to
    > Private APN -\> Scan Internal IP -\> Attack Backend Servers

-   **AI分析**：Qwen-VL-OCR扫描T-BOX固件的Hex
    > Dump，识别出类似密码的字符串，结合代码审计Agent，发现硬编码凭证 。

#### **场景 3：FOTA 更新包篡改**

-   **威胁**：攻击者劫持更新流量，下发恶意固件。

-   **防御检查**：平台自动检查T-BOX的"安全启动（Secure
    > Boot）"和"验签（Signature Verification）"流程。如果图谱中显示
    > (FOTA Package)\--\>(Public Key) 关系缺失，则标记为Critical风险。

## **11. 总结与展望**

构建面向汽车行业的智能TARA平台，是应对SDV时代安全挑战的必然选择。本报告提出的架构方案，创新性地融合了
**图数据库** 的结构化关联能力与 **阿里云Qwen多模态大模型**
的非结构化理解能力。

1.  **解决了"输入难"的问题**：利用Qwen-VL，能够自动化处理大量遗留的工程图纸和文档，大幅降低了TARA启动的数据准备门槛。

2.  **解决了"分析浅"的问题**：利用图数据库（Neo4j），能够发现跨域、多跳的深层攻击路径，这是传统人工分析无法企及的深度。

3.  **解决了"更新慢"的问题**：通过自动化的流水线，当BOM发生变更或新CVE爆发时，平台可实时重算风险，实现了持续的网络安全监控（Continuous
    > Monitoring）。

对于IVI和T-BOX这两个关键平台，本方案提供的不仅是工具，更是系统化的安全思维。未来，随着大模型推理能力的进一步增强，该平台有望从"辅助分析"进化为"自动防御"，即自动生成安全需求（Security
Requirements）并注入到开发流程中，真正实现"设计即安全"（Security by
Design）的愿景。
